How it works

One machine runs the pool. Everyone else brings theirs. Work goes to whichever machine is free, and each job gets a fresh VM or sandbox that is thrown away after.

  1. Step 1

    Lay out the blanket

    On one machine, start a pool for your team and make invite codes. Potluck has no accounts of its own. Your machines find each other over Tailscale, so the first time it gives you a Tailscale login link (a free Tailscale account); --via tunnel skips Tailscale and uses a tunnel you set up to the machine that runs the pool (a public https address). To try it alone on one machine there is nothing to set up: potluck create trial --via tunnel.

    $ potluck create friends
$ potluck invite sam --host   # invite code for Sam

  2. Step 2

    Friends bring their machines

    Bring every computer you can spare: the old gaming PC, the Mac mini, the rented server, a cloud VM with hours left over. Put each one in one pool or several: your friends' project, your startup, an open source project. A machine joins only if its checks pass.

    $ potluck doctor
$ potluck host '<code>'

  3. Step 3

    Leo wants his Mac back

    A Mac works for the team only while its owner is away: when Leo touches the keyboard or trackpad, the job on his MacBook ends, and nothing new starts until it has been idle for five minutes (potluck host --reclaim-idle-s changes that; 0 shares all the time). When he wants the machine back for good, he winds it down: jobs running now finish (up to 30 minutes by default) and no new ones start. Or he stops them now. potluck host set auto puts it back to normal. The picture shows a Mac set to share all the time (--reclaim-idle-s 0); by default, touching the trackpad would already have ended those jobs. The release carries a menu bar item for this: sh install.sh --menubar installs it (it isn't signed by Apple yet, so a copy downloaded in a browser needs a right-click, Open; docs/menubar.md). Without it, it's one command.

    $ potluck host set drain    # wind down
$ potluck host set closed   # stop now

What you can do with it

Coding agents

Give your agent a computer of its own

Your agent's commands run in a throwaway sandbox on a pool machine, not on your laptop.

$ potluck sandbox create   # prints its id
$ potluck sandbox exec <id> -- make test
$ potluck sandbox rm <id>

Or hand it the sandbox tools over MCP:

{"mcpServers":{"potluck":{"command":"potluck","args":["mcp"]}}}

Using Claude Code's self-hosted runner? Run it in fresh sandboxes:

$ potluck agent-runner claude --secret-file <key-file>

GitHub Actions

Move a macOS job onto your own Mac

One command prepares a change to one line of your workflow; then open the pull request it prepares. Your own branches run on the lent Mac. Pull requests from forks keep using GitHub's runner.

$ potluck ci pr acme/app
.github/workflows/ci.yml
- runs-on: macos-15
+ runs-on: your Mac (GitHub's for forks)

Simplified. The exact line it writes.

House rules

Four things to know before you lend a machine. The full list is on GitHub.

  1. Work stays in a box

    Every job runs in a throwaway VM or sandbox, not directly on your machine, and is deleted after.

  2. Keys go only where you send them

    A job gets a secret only when you grant it, only on a friend's machine, and as a file: never on the command line or in its environment.

  3. Friends and strangers

    Mark each machine as a friend's or a stranger's. A friend's machine takes your jobs and the keys you grant. A stranger's runs only the sandboxes you send it, and never gets a key.

  4. Share the Mac you already own

    Stop paying by the minute for Mac builds. Lend your Mac's spare time to your team and friends and save them thousands. Apple's licence forbids selling Mac time, not lending a macOS VM to your team.*

* That's our reading of Apple's macOS licence; read it yourself before you lend. Linux VMs on a Mac aren't affected.
